# Enigma2 MQTT Bridge - PRD and delivery blueprint

**Version 1.0 of this document, 2026-09-16. Status: awaiting operator approval; no repository
created, no code written.** Technical basis: [vuplus-mqtt-plugin.md](vuplus-mqtt-plugin.md)
(measured box facts, hook tables, topic design). This document turns that private design into
a **public product**: an Enigma2 plugin and a Home Assistant integration, both under
`deltasystems-pl`, published through the Enigma2 feeds and HACS, developed in the open from the
first commit.

---

## 0. Summary

Enigma2 receivers (Vu+, Dreambox, Zgemma, Octagon, ... running OpenViX, OpenATV, OpenPLi, OpenBH)
reach Home Assistant today only through OpenWebif **polling** - the core `enigma2` integration
asks every 15 s and drives everything through REST calls whose result must be read back from
the body. **Enigma2 MQTT Bridge** replaces that with a push model:

- **The plugin** (`enigma2-plugin-extensions-mqttbridge`) runs inside enigma2, keeps one MQTT
  session to the user's broker, publishes state **the moment enigma2 raises the event**
  (zap, EPG change, standby, recording, volume, remote key), announces itself with standard
  HA MQTT discovery, and executes commands received on the same session.
- **The integration** (`enigma2_mqtt`, HACS) consumes the same topics and adds what MQTT
  discovery cannot express: a native `media_player` with channel browsing, a `remote`, a
  `notify` target for on-screen messages, device triggers for remote keys, an `update` entity,
  and a guided installer that puts the plugin on the box over SSH.

Either half works alone. The plugin without the integration gives discovery entities plus a
documented `universal` media_player recipe; the integration without the plugin does nothing
except offer to install it.

## 1. Goals and non-goals

**Goals**

1. Sub-second state in HA for the things a household automates on: current channel, standby,
   recording, programme, volume, remote keys.
2. Two-way: everything OpenWebif can be told (zap, power, volume, keys, OSD message, timers) is
   an MQTT command with a verified result.
3. Availability that tells the truth: broker last-will within 45 s instead of a 10-minute poll watchdog.
4. Installable by a non-developer: plugin from the image's plugin browser or a one-line `opkg`,
   integration from HACS, box provisioning from the HA UI.
5. Fully public development: repositories, issues, CI, releases, changelogs, security policy.

**Non-goals (v1)**

- Streaming video through the plugin (OpenWebif and go2rtc already do that).
- Full EPG grids or search over MQTT (pull by nature; stays on OpenWebif).
- Python 2 images (VTi). Dreambox OE 2.x with Python 2 is out of scope.
- Replacing OpenWebif. The plugin is a bridge, not a web UI.
- Multi-broker, MQTT 5 features, or bridging several boxes through one plugin instance.

## 4. System overview

```
┌──────────────────── Enigma2 box ────────────────────┐        ┌────────────── Home Assistant ──────────────┐
│ enigma2 (Twisted reactor, main thread)              │        │                                             │
│  ├─ MQTTBridge plugin                               │  MQTT  │  core `mqtt` integration                    │
│  │   hooks: standby · nav.event · record_event      │◄──────►│   └─ discovery entities  (plugin-only mode) │
│  │          VolumeControl · eActionMap · RecordTimer│ broker │                                             │
│  │   publishes: enigma2/<node>/...  (retained JSON) │        │  `enigma2_mqtt` integration (HACS)          │
│  │   announces: enigma2mqtt/discovery/<node>/config │        │   ├─ media_player · remote · notify · event │
│  │   subscribes: enigma2/<node>/cmd/#               │        │   ├─ sensors · switches · buttons · image   │
│  │   paho thread ─callFromThread─► main loop        │        │   ├─ update (bundled IPK vs box)            │
│  └─ OpenWebif (unchanged; used only by the installer│  SSH   │   └─ installer: opkg install + provisioning │
│       preflight and as the screenshot URL fallback) │◄───────│                                             │
└──────────────────────────────────────────────────────┘        └─────────────────────────────────────────────┘
```

Two HA modes, chosen by the plugin's `ha_mode` setting and switchable by the integration
(the Tasmota pattern: `SetOption19` vs. the native Tasmota integration):

- **`discovery`** (default) - the plugin publishes standard HA MQTT discovery; HA's core MQTT
  integration creates the entities. No custom integration needed.
- **`integration`** - the plugin publishes only its announcement; `enigma2_mqtt` builds every
  entity. The integration switches a box into this mode on setup (`cmd/ha_mode`), and the
  plugin **retracts** its discovery payloads first, so entities are never duplicated.

**Provisioning file** `/etc/enigma2/mqttbridge.json`: if present at plugin start, its keys are
written into the config, the file is **deleted** (it holds the password), and the plugin
proceeds. This is the only mechanism the installer and headless deploys use; the setup screen
shows the same values afterwards.

### 5.4 Behaviour

- **Lifecycle**: `WHERE_SESSIONSTART` (needs the session) and `WHERE_AUTOSTART` reason 1
  (clean disconnect on shutdown). Invalid or missing config -> one log line, plugin idle; the
  GUI must never fail to start because of the bridge.
- **Connection**: paho `loop_start()` on its own thread; every callback marshals to the main
  loop with `reactor.callFromThread` (fallback `ePythonMessagePump`); keepalive 30 s;
  reconnect 1->60 s backoff; LWT `.../availability = offline` retained; **`on_connect` publishes
  `online`, the full state snapshot, the announcement and (in `discovery` mode) the discovery
  payloads - every time**.
- **State topics** (retained JSON under `enigma2/<node>/`): `power`, `service`, `epg`, `tuner`,
  `recording`, `timers`, `volume`, `hdd`, `info`, `screen` (raw JPEG), `last_error`;
  `key` not retained. Field-level contract in the design doc §4.2 and in `docs/TOPICS.md`.
- **Announcement** `enigma2mqtt/discovery/<node>/config` (retained JSON): node_id, friendly
  name, base topic, image/enigma/plugin versions, boxtype, MAC, IP, capabilities list,
  `ha_mode`. This is what the integration discovers.
- **Commands** `enigma2/<node>/cmd/<name>` (QoS 1, never retained): `power`, `deep_standby`,
  `reboot`, `restart_gui`, `zap`, `volume`, `mute`, `key`, `message`, `timer`, `record`,
  `screenshot`, `discovery`, `ha_mode`, `reset` (retract every retained topic). Every command is
  **verified by effect** and answered on its state topic; failures go to `last_error`.
- **Guards**: deep standby / reboot / GUI restart refused while recording or with a timer due
  in 10 min; `zap` by name refused when the name is not unique; key handler always
  `return 0`; publishes never block; `grab` runs via `eConsoleAppContainer`; ≤ 1 screenshot per 5 s.
- **Retained hygiene**: `components.json` remembers what was announced; renamed or removed
  components are retracted before the new announcement; `cmd/reset` retracts everything
  (the documented step before uninstall).

### 6.2 Config flow

1. **Discovered** - the announcement arrives on `enigma2mqtt/discovery/#` -> `async_step_mqtt`
   -> confirm card „Enigma2 box *Dekoder salon* (Vu+ Uno 4K SE, OpenViX 6.6.007)". Unique id =
   `node_id`. On confirm the integration publishes `cmd/ha_mode = integration` and waits for
   the ack on `info`.
2. **Manual** - base topic + node id, for boxes behind a bridge or with a custom prefix.
3. **Install the plugin** (optional branch, also reachable from the device page later):
   host, SSH user/password (root on most images) -> **preflight** over SSH: image, Python ≥ 3.9,
   free space, whether the plugin is already installed, OpenWebif `/api/timerlist` idle ->
   upload the **bundled IPK** through an `ssh exec` stream (dropbear has no SFTP) ->
   `opkg install` -> write `mqttbridge.json` (broker host/port/user/password, node id, `ha_mode`
   = `integration`) -> guarded GUI restart -> wait ≤ 120 s for the announcement. The SSH
   password is **discarded after a successful install** unless the user unticks „keep for
   updates". Every step is reported in the flow; a failure leaves the box as it was (the IPK
   is removed if it was ours and the install did not finish).
4. **Broker credentials**: v1.0 asks for them, with help text and an ACL snippet for the
   Mosquitto add-on. v1.1 offers „create a broker login for this box" when the Supervisor and
   the Mosquitto add-on are present (add-on options + restart, with an explicit consent step).
5. **Reconfigure** and **options** (screenshot policy, key events, deep-standby button
   visibility, WoL MAC, which bouquets to browse).

### 6.4 Actions (services)

`enigma2_mqtt.zap` (sref | name), `send_key` (key, long), `message` (text, type, timeout),
`add_timer` (sref + event_id, or sref + begin + end + name), `delete_timer`, `record`
(start/stop), `screenshot`, `set_ha_mode`. All take a device or entity target and return the
plugin's verified result or raise `HomeAssistantError` with `last_error`.

### 6.5 Quality bar

Config flow with discovery, reconfigure and options; unique ids everywhere; `diagnostics.py`
(redacts broker and SSH secrets); entity translations en/pl/de; `PARALLEL_UPDATES = 0` (push);
unit tests for payload parsing, the installer state machine (with a fake SSH server) and the
config flow; `hassfest` and the HACS action green in CI. The measurable target is the HA
integration quality scale "silver" behaviours, documented in `docs/QUALITY.md` even though a
custom integration cannot claim the badge.

## 7. Security and privacy

- **Threat model**: most Enigma2 boxes run telnet/ssh with the image's default root password.
  The broker credential therefore lives on a box that must be assumed reachable by anyone on
  its LAN. Mitigations: dedicated broker login per box; documented ACL limiting it to
  `enigma2/<node>/#`, `enigma2mqtt/discovery/<node>/#`, `homeassistant/+/<node>*/#`; the
  README's first security note tells users to change the root password.
- **The integration stores an SSH password only if asked to**, in the config entry (HA's
  `.storage` is not encrypted at rest - documented), and never writes it to logs or diagnostics.
- **No telemetry, no cloud, no outbound connection** other than the user's broker; the GitHub
  release check is opt-in.

  > **Superseded in part by [ADR-0008](0008-signed-plugin-index.md) (proposed, 2026-09-26):** the
  > integration is to fetch the plugin's signed release index and plugin packages from the plugin's
  > fixed origin when a person asks for it, when an install needs it, or when the opt-in daily check
  > is on; to ask GitHub's API once per install to cross-check a package's digest; and to serve a
  > verified package on the LAN to a receiver without internet. The supply-chain bullet below gains
  > that second source beside the bundle. Until ADR-0008 is accepted and shipped, the bullet above
  > describes every released integration exactly. No telemetry and no cloud service are unchanged.
- **Privacy of `key` and `epg` topics**: they reveal what is watched and pressed. The README
  recommends recorder exclusions; the plugin can disable key publishing.
- **Supply chain**: paho vendored at a pinned version with its sha256 recorded in `NOTICE`;
  CI builds the IPK from the tag and publishes the sha256; the integration bundles the IPK of
  the same release and verifies the hash before upload.
- `SECURITY.md` in both repositories: private disclosure via GitHub security advisories,
  acknowledgement within 7 days, fix or mitigation before publication.

### 8.3 Release process (both repositories)

- Semantic versioning; tags `vX.Y.Z`; a GitHub Release per tag with notes copied from
  `CHANGELOG.md` (Keep-a-Changelog format, an `Unreleased` section always present).
- Plugin `release.yml`: build IPK -> sha256 -> attach -> regenerate the feed on the `gh-pages`
  branch. Integration `release.yml`: hassfest + HACS action -> copy the plugin IPK of the
  pinned version into `custom_components/enigma2_mqtt/assets/` -> attach a zip.
- Compatibility matrix `integration <-> plugin` in both READMEs; the integration warns on the
  `update` entity when the box runs a plugin older than its bundled one.
- Pre-release tags `v0.x` for beta testers, announced in a GitHub Discussion and a
  call-for-testers issue per image.

### 8.4 Transparency rules

1. Both repositories are **public from the first commit**; nothing is developed privately and
   pushed later.
2. Every change lands through a **pull request with CI green**, even from the sole maintainer -
   the PR is the public record of *why*.

## 9. Engineering process

- **Layout**: two repositories (§5.2, §6.1); the operator's lab keeps only a pointer in
  `pve-ai` (this doc, the design doc, and a private `deploy` note with the box's secrets in
  `secrets.local.md`).
- **Dev loop, plugin**: unit tests on the PC against a stub `enigma` module; then
  `tools/deploy-to-box.sh` (scp `-O`, `opkg install`, guarded `killall enigma2`), tail
  `/home/root/mqttbridge.log` and `mosquitto_sub -v -t 'enigma2/#'`. The only known PC-side
  enigma2 sandbox (`technic/enigma2_example`, Docker + VNC + ptvsd) targets **Python 2** and
  has four commits, so it is not a runtime for this plugin; the operator's box stays the only
  runtime and the stub `enigma` module carries the unit tests. Forking the sandbox onto a
  Python 3 enigma2 build is a §10 M7 candidate, not a prerequisite.
- **Dev loop, integration**: `pytest` with `pytest-homeassistant-custom-component`, a fake MQTT
  broker fixture and a fake SSH server for the installer; live test on the operator's HA.
- **CI gates**: ruff + pyflakes (the danfoss `NameError` that broke every poll is the reason),
  tests on 3.9/3.12/3.14 (plugin) and the current HA (integration), IPK build, hassfest,
  HACS action. A release tag is refused unless CI is green and the changelog has the version.
- **By-effect checklist on the box** (from the design doc §7): zap -> `service`/`epg`/`screen`
  within 3 s; volume from remote, OpenWebif and HA; standby in/out; a 1-minute recording;
  colour keys short/long; every `cmd/*` read back; LWT drill (cable out 60 s -> `unavailable`
  ≤ 45 s -> back); 1-hour soak with a 1 s command loop and no traceback; watchdog restart
  interplay; deep standby + WoL in a separate window.
- **Definition of done**, every milestone: CI green, docs updated, changelog entry, the by-effect
  checklist run on the operator's box, and the wiki/pve-ai pointer refreshed.

## 11. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A plugin exception freezes the GUI on someone's box | reputational, support load | every hook wrapped; no blocking I/O on the main thread; soak test; `enabled` toggle reachable from the setup screen even when the broker is down |
| Hook names differ on OpenPLi/OpenBH | features silently missing | per-hook capability detection reported in `info.capabilities`; the integration hides what the box cannot do; testers per image |
| paho thread + enigma2 interplay on Python 3.14 | crash on OpenBH | the thread bridge is the only cross-thread path; CI runs the pure-Python parts on 3.14; twisted-mqtt (no thread) is the documented plan B |
| Users run the box with `root/root` | credential leak | ACL guidance, dedicated login, warning in the README and in the setup screen |
| HACS default review takes months | discoverability | custom-repo instructions from day one; 3rd-party feed for the plugin does not depend on it |
| Vendored paho drifts from upstream | security patches missed | Dependabot-style check in CI (compare tag), pinned hash, changelog entry per bump |
| Operator's own box is the only runtime | image bugs unseen | call-for-testers per image before `v1.0`; capability detection instead of assumptions |
| The `workflow` token scope is never granted | no public CI | the PRD makes it a prerequisite for M1; without it the repos are not created |
